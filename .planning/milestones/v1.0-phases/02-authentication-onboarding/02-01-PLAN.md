Harden backend authentication with HttpOnly cookies, refresh token rotation, and bcrypt 13 rounds.

Output: Updated backend auth routes using cookies, new refresh_tokens table, cookie-aware middleware, updated OAuth callbacks.
</objective>

1. Update `packages/backend/src/api/auth.ts`:

   **Helper function** - Create a `setAuthCookies(reply, accessToken, refreshToken)` helper and a `clearAuthCookies(reply)` helper at the top of the file to avoid duplication. Cookie settings:
   - accessToken: httpOnly, secure (NODE_ENV=production), sameSite='lax' (NOT strict - strict blocks OAuth redirects), path='/', maxAge=900 (15min)
   - refreshToken: httpOnly, secure (NODE_ENV=production), sameSite='lax', path='/api/auth', maxAge=604800 (7d)

   **Helper function** - Create `issueTokenPair(fastify, user)` that generates access token (15min, payload: {userId, email, role}) and refresh token (7d, payload: {userId, type: 'refresh'}), stores refresh token hash (bcrypt 10 rounds for tokens, not passwords) in refresh_tokens table, and returns both.

   **POST /api/auth/signup**:
   - Increase bcrypt rounds from 10 to 13 for password hashing
   - Lowercase email before checking existence and inserting
   - After creating user, call `issueTokenPair`, then `setAuthCookies`
   - Return `{ user: {...} }` WITHOUT token in body (tokens are in cookies now)

   **POST /api/auth/login**:
   - Lowercase email for lookup
   - After password verification, call `issueTokenPair`, then `setAuthCookies`
   - Return `{ user: {...} }` WITHOUT token in body

   **POST /api/auth/refresh** (NEW endpoint):
   - Read refreshToken from `request.cookies.refreshToken`
   - If missing, return 401
   - Verify JWT signature and check `type === 'refresh'`
   - Look up refresh_tokens row for user_id where expires_at > now()
   - Verify bcrypt hash matches stored token_hash
   - If invalid, return 401 and delete ALL refresh tokens for this user (potential token reuse attack)
   - If valid: delete old refresh token, issue new token pair, set new cookies
   - Return `{ success: true }`

   **GET /api/auth/me**:
   - No changes needed (authenticate middleware handles cookie reading)
   - Keep as-is

   **POST /api/auth/logout**:
   - Delete ALL refresh tokens for the user from database
   - Call `clearAuthCookies(reply)` to clear both accessToken and refreshToken cookies
   - Return `{ success: true }`
   - NOTE: Keep `onRequest: [authenticate]` but make it graceful - if no valid token, still clear cookies and return success

2. Update `packages/backend/src/api/auth-oauth.ts`:

   **Google callback**: Instead of `reply.redirect(FRONTEND_URL/auth/callback?token=...)`, use `issueTokenPair` + `setAuthCookies`, then redirect to `FRONTEND_URL/auth/callback` (no token in URL). Import the helper functions from auth.ts or duplicate them in this file.

   **GitHub callback**: Same change - set cookies, redirect without token in URL.

   Since auth.ts and auth-oauth.ts are separate Fastify plugins, the cleanest approach is to extract the cookie helpers and token issuance into a shared utility. Create the helpers at the top of auth.ts and export them, then import in auth-oauth.ts. Alternatively, define them in a small `packages/backend/src/utils/auth-cookies.ts` file if the circular dependency is cleaner.

3. Update `packages/backend/src/middleware/auth.ts`:

   ```typescript
   export async function authenticate(request: FastifyRequest, reply: FastifyReply) {
     try {
       // @fastify/jwt with cookie config will check cookie automatically
       // but we also want to support Authorization header for API clients
       await request.jwtVerify();
     } catch (err) {
       return reply.code(401).send({ error: 'Unauthorized' });
     }
   }
   ```
   The @fastify/jwt `cookie` config in index.ts handles reading from cookies. If someone passes an Authorization header, it takes precedence. No code change needed in the middleware itself -- but verify this works correctly with the cookie config.
