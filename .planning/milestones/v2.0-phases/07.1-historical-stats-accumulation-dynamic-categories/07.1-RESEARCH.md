# Phase 07.1: Historical Stats Accumulation & Dynamic Categories - Research

**Researched:** 2026-02-21
**Domain:** ESPN API per-period stats extraction, component-based stat accumulation, dynamic category configuration
**Confidence:** HIGH

## Summary

Phase 07.1 fixes broken historical backfill by switching from team-level cumulative stats (which ESPN returns identically for all weeks) to per-period player-level stats accumulated across time. The core problem: ESPN's `valuesByStat` on teams returns full-season cumulative totals regardless of `scoringPeriodId` parameter. The solution involves extracting per-period player stats from roster entries, filtering to active lineup slots, aggregating to team-level per-period totals, accumulating across periods to build running totals, and using league-defined scoring categories instead of hardcoded lists.

**Primary recommendation:** Use existing component-based formula infrastructure (`packages/shared/src/formulas.ts`) for rate stat accumulation. ESPN per-period player stats are located in `playerPoolEntry.player.stats[]` array with `statSplitTypeId=5`. Filter roster entries by `lineupSlotId` (exclude 16=bench, 17=IL, 19=NA). League scoring categories already stored in `league_settings_version.settings_json.categories` — use this as source of truth, not hardcoded lists.

### Pattern 2: Component-Based Stat Accumulation
**What:** Sum counting stat components across players/periods, compute rate stats from accumulated totals
**When to use:** Building running totals for each week's standings
**Example:**
```typescript
// Source: packages/shared/src/formulas.ts (existing code)
import { combineComponents, calculateFinalRate } from "shared/formulas.js";

// Accumulate components for a team across active roster
const teamComponents: StatComponents = { AB: 0, H: 0, ER: 0, IP: 0 };
for (const player of activeRoster) {
  teamComponents.AB += player.AB || 0;
  teamComponents.H += player.H || 0;
  // ... etc for all components
}

// Compute rate stat from accumulated components
const teamAVG = calculateFinalRate("avg", {}, teamComponents);
// Never: const teamAVG = avgOf(player1.AVG, player2.AVG, ...) — WRONG
```

### Anti-Patterns to Avoid
- **Averaging rate stats across periods:** `(week1_AVG + week2_AVG) / 2` is mathematically wrong. Always accumulate components (H, AB) and compute rate from totals.
- **Using bench/IL players in totals:** ESPN scoring only counts active lineup. Filter by `lineupSlotId` before aggregating.
- **Hardcoding category lists:** League settings can change mid-season. Always fetch from `league_settings_version.settings_json.categories`.
- **Assuming statSplitTypeId=5 always exists:** Per-period stats may not exist for early weeks (1-9) or all players. Treat missing as zero contribution.

## Common Pitfalls

### Pitfall 1: Treating OUTS as IP
**What goes wrong:** ESPN uses stat ID 34 (OUTS) not IP. 3 outs = 1 inning pitched.
**Why it happens:** Baseball stats typically shown as IP (e.g., 6.1 IP = 19 outs).
**How to avoid:** Convert OUTS to IP before passing to formulas: `IP = OUTS / 3`
**Warning signs:** ERA/WHIP values 3x higher than expected, division-by-zero errors

### Pitfall 2: Per-Period Stats Missing for Early Weeks
**What goes wrong:** `statSplitTypeId=5` entries may not exist for weeks 1-9 (only 10-26 available).
**Why it happens:** ESPN API data structure varies by season stage.
**How to avoid:** Check if `playerStats` is undefined before accessing. Treat missing as zero contribution for that player/week.
**Warning signs:** Backfill succeeds but standings show zero totals for early weeks

### Pitfall 3: Including Bench/IL Players in Totals
**What goes wrong:** Standings totals include bench players, inflating stats incorrectly.
**Why it happens:** All roster entries present in ESPN response, not just active lineup.
**How to avoid:** Filter roster entries: `entry.lineupSlotId <= 15` (exclude 16=bench, 17=IL, 19=NA)
**Warning signs:** Team totals higher than ESPN official standings, rate stats skewed

### Pitfall 4: Hardcoded Category Lists on Frontend
**What goes wrong:** Dropdown shows categories league doesn't use (e.g., HLD in league without holds).
**Why it happens:** Trends page has static `categories` array (lines 192-204).
**How to avoid:** Fetch categories from `/standings/projected` API (already returns categories array).
**Warning signs:** User selects category, no data appears because league doesn't track it

### Pitfall 5: Rate Stat Component Mismatch
**What goes wrong:** AVG calculated from wrong components (e.g., using HA instead of H for batting average).
**Why it happens:** Pitcher stats use HA (hits allowed), batter stats use H (hits).
**How to avoid:** ESPN stat map distinguishes: stat 1=H (batting), stat 37=HA (pitching). Check `ESPN_STAT_MAP` in espn.ts.
**Warning signs:** Batting average shows as 0 when pitcher stats are present

## Code Examples

Verified patterns from official sources:

### Extracting Per-Period Player Stats
```typescript
// Source: ESPN API structure (from community documentation)
// https://stmorse.github.io/journal/espn-fantasy-v3.html
// https://thomaswildetech.com/projects/espn/player-info-json-views/

function extractPlayerPeriodStats(
  rosterEntry: any,
  scoringPeriodId: number,
  espnStatMap: Record<number, { key: string }>
): Record<string, number> {
  const stats: Record<string, number> = {};

  // Find stats entry for this period
  const playerStats = rosterEntry.playerPoolEntry?.player?.stats?.find(
    (s: any) => s.scoringPeriodId === scoringPeriodId && s.statSplitTypeId === 5
  );

  if (!playerStats) {
    return stats; // No stats for this period — treat as zero contribution
  }

  // Map ESPN stat IDs to canonical keys
  for (const [espnStatId, value] of Object.entries(playerStats.stats)) {
    const mapped = espnStatMap[parseInt(espnStatId, 10)];
    if (mapped) {
      stats[mapped.key] = value as number;
    }
  }

  // Convert OUTS to IP (3 outs = 1 IP)
  if (stats.OUTS !== undefined) {
    stats.IP = stats.OUTS / 3;
  }

  return stats;
}
```

### Aggregating Team-Level Components from Roster
```typescript
// Source: TypeScript reduce patterns for accumulation
// https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/reduce
// https://geeksforgeeks.org/typescript/typescript-array-reduce-method/

function aggregateTeamComponents(
  activeRoster: Array<{ stats: Record<string, number> }>
): StatComponents {
  return activeRoster.reduce((teamTotal, player) => {
    // Sum each component across all active players
    for (const [key, value] of Object.entries(player.stats)) {
      teamTotal[key] = (teamTotal[key] || 0) + (value || 0);
    }
    return teamTotal;
  }, {} as StatComponents);
}
```

### Computing Rate Stats from Accumulated Components
```typescript
// Source: packages/shared/src/formulas.ts (existing code)
import { calculateFinalRate, getRequiredComponents } from "shared/formulas.js";

function computeRateStatValue(
  category: Category,
  teamComponents: StatComponents
): number {
  if (category.type === "COUNTING") {
    // Direct value from components
    return teamComponents[category.stat_key] || 0;
  } else if (category.type === "RATE" && category.formula_id) {
    // Compute from accumulated components
    return calculateFinalRate(category.formula_id, {}, teamComponents);
  }
  return 0;
}
```

## Open Questions

1. **Do per-period stats exist for weeks 1-9?**
   - What we know: Additional context mentions statSplitTypeId=5 may only be available for weeks 10-26
   - What's unclear: Whether early weeks have different statSplitTypeId or are truly missing
   - Recommendation: Handle gracefully by treating missing as zero contribution, log warning for debugging

2. **How to handle mid-season category changes?**
   - What we know: `league_settings_version` has `effective_date` field to track settings changes
   - What's unclear: Whether ESPN allows mid-season category changes in practice
   - Recommendation: Use `effective_date` to select correct settings version for each snapshot date

3. **Should we store per-period player stats in DB?**
   - What we know: Current schema only stores team-level daily totals (`team_daily_category_totals`)
   - What's unclear: Whether individual player per-period stats have value for future features
   - Recommendation: Start by only storing team-level aggregates (keeps schema simple), add player-level table if needed later
