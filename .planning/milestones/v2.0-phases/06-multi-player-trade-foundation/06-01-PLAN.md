**2. Add `validateRosterSlots()` to `TradeRecommendationAgent` in `packages/backend/src/agents/trade-recommendation.ts`:**

Add a public method `validateRosterSlots()` that:
- Accepts: `leagueId: number, teamId: number, snapshotDate: string, trade: ProposedTrade`
- Returns: `Promise<RosterValidationResult>`
- Implementation:
  1. Fetch the team's current roster (reuse `getTeamRoster()`)
  2. Fetch league settings to get `roster_slots` from `settings_json`
  3. Build post-trade roster: remove givePlayers, add receivePlayers (fetch positions for received players from the `player` table)
  4. Run greedy slot assignment in specificity order: C, 1B, 2B, 3B, SS, OF, SP, RP, P, UTIL, BN, IL (process specific slots first, then generic slots)
  5. For each slot type, count how many slots need filling and iterate unassigned players checking eligibility
  6. `canFillSlot()` helper: UTIL/BN accept any player; P accepts SP or RP; IL accepts any player; specific slots require exact position match in player.positions array
  7. After processing all slots, any unassigned non-IL players produce an issue
  8. Return `{ isLegal: issues.length === 0, issues }`

Important implementation details:
- Roster slot keys come from `league_settings_version.settings_json.roster_slots` which is `Record<string, number>`
- Player positions come from `player.positions` which is `string[]`
- Sort slot types by specificity so C-eligible players fill C slots before UTIL slots
- Handle the case where received players may not be in the player table yet (fetch from DB, skip validation for unknown players with a warning)

Also add a static method `validateTradeSize(trade: ProposedTrade): { valid: boolean; error?: string }` that:
- Checks `trade.givePlayers.length >= 1 && trade.givePlayers.length <= 3`
- Checks `trade.receivePlayers.length >= 1 && trade.receivePlayers.length <= 3`
- Returns appropriate error messages

**Test Group 1: Component Math Accuracy (TRADE-04)**

These tests verify that `simulateTradeImpact` uses component aggregation, not rate averaging. Since `simulateTradeImpact` is a private method, test through the public `analyzeTradeImpact()` method with mocked DB responses.

Create a helper to build a mock Kysely DB that returns controlled data:
- Mock `league_daily_snapshot` to return a valid snapshot
- Mock `team_daily_projected_overall` to return current standings
- Mock `team_daily_projected_category` to return current category projections with known components
- Mock `team_roster_snapshot` joined with `player` to return a known roster
- Mock `player_projection` to return known stat_components_json for each player
- Mock `league_settings_version` to return categories including AVG, ERA, HR, RBI

Test cases:

a) **2-for-2 batter trade AVG accuracy:**
   - Team has projected AVG components: H=500, AB=2000 (AVG=.250)
   - Give Player A (H=50, AB=200, .250) and Player B (H=30, AB=100, .300)
   - Receive Player C (H=60, AB=200, .300) and Player D (H=45, AB=150, .300)
   - Post-trade components: H = 500 - 50 - 30 + 60 + 45 = 525, AB = 2000 - 200 - 100 + 200 + 150 = 2050
   - Expected AVG: 525/2050 = 0.25610 (NOT the naive average of player rates)
   - Use `expect(avgImpact.projectedValue).toBeCloseTo(0.2561, 3)`
   - Verify it's NOT `toBeCloseTo(0.300, 3)` (which would be the averaged rate of received players)

b) **3-for-1 pitcher trade ERA accuracy:**
   - Team has projected ERA components: ER=200, IP=500 (ERA=3.60)
   - Give Player A (ER=10, IP=50), Player B (ER=15, IP=40), Player C (ER=5, IP=30)
   - Receive Player D (ER=20, IP=100)
   - Post-trade: ER = 200 - 10 - 15 - 5 + 20 = 190, IP = 500 - 50 - 40 - 30 + 100 = 480
   - Expected ERA: 9 * 190 / 480 = 3.5625
   - `expect(eraImpact.projectedValue).toBeCloseTo(3.5625, 2)`

c) **Counting stat accuracy for multi-player trade:**
   - Give 2 players with HR projections of 15 and 10
   - Receive 2 players with HR projections of 20 and 8
   - Net HR delta: (20+8) - (15+10) = +3
   - Verify HR projected value increases by exactly 3
