**Step 0: Analyze Task 1 diagnostic output and select fix approach.**

Read through the Task 1 debug output and apply this decision tree to determine the fix:

1. **Check active roster counts.** If active roster count is less than 10 per team (expected 20-25), the `lineupSlotId` filter is too aggressive. Fix: adjust the filter threshold or use a whitelist of active slot IDs (0-15 inclusive based on ESPN baseball slots: 0=C, 1=1B, 2=2B, 3=3B, 4=SS, 5-8=OF, 9-10=DH, 11=IF, 12=UTIL, 13=P, 14=SP, 15=RP). Examine the actual `lineupSlotId` values being excluded to determine the correct filter.

2. **Check stat values per player.** If stat values are fractional (e.g., 0.3 HR instead of 3 HR), then `statSplitTypeId=5` returns per-game or daily averages, not per-period totals. Fix: either switch to `statSplitTypeId=0` (season cumulative) and compute per-period deltas, or aggregate all `statSplitTypeId=5` entries across the period's games.

3. **Check stats[] entry count per player.** If players have multiple `stats[]` entries matching the same `scoringPeriodId + statSplitTypeId=5` and the code uses `.find()` (returns only the first), we are capturing only one game's stats. Fix: replace `.find()` with `.filter()` and sum stat values across all matching entries.

4. **Check priorComponents.** If `priorComponents` is always empty/zero even for weeks after week 1, the cumulative accumulation is broken. Fix: trace the `previousSnapshotDate` propagation from historical-backfill.ts through to the DB query for prior components, and fix the broken link.

5. **If multiple issues found:** Apply all relevant fixes.

Apply the appropriate fix(es) based on observed evidence.
