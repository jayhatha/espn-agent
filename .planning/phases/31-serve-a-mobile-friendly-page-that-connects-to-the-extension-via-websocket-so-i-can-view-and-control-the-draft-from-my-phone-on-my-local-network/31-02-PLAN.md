<objective>
Wire the Chrome extension into the WebSocket relay pipeline: write engine signals to chrome.storage.local from the content script, connect the background service worker as a WS client to the Fastify hub, and handle bidirectional message relay (state out, controls in).

Purpose: The extension is the data source — it has the draft state and computed engine signals. The background SW acts as the bridge between the extension's in-page context and the Fastify WS hub. Engine signals must be explicitly written to storage because they're computed in React context (content script) which the background SW cannot access directly.

Output: Modified background.ts with WS client + reconnect + keepalive + relay logic. Modified DraftSidebar.tsx to persist engine signals to storage. Modified content.tsx with CONTROL command listener.
</objective>

```typescript
// Listen for CONTROL commands from the background service worker (relayed from mobile)
chrome.runtime.onMessage.addListener((message, _sender, sendResponse) => {
  if (message.type !== "CONTROL") return false;

  const store = useDraftStore.getState();

  switch (message.action) {
    case "SET_AUTO_MODE":
      store.setAutoMode(message.payload as boolean);
      break;
    case "SET_POSITION_FILTER":
      store.setPositionFilter(message.payload as string | null);
      break;
    case "TOGGLE_SIDEBAR":
      store.toggleSidebar();
      break;
    case "SET_PITCHER_HITTER_SPLIT":
      store.setPitcherHitterSplit(message.payload as number);
      break;
  }

  sendResponse({ ok: true });
  return false;
});
```

Place this listener right after the `leagueId` check (around line 63, after the "Draft detected" log). It must be before the React root mount so it's active even if the sidebar UI hasn't rendered yet.

The supported control actions for v1:

- `TOGGLE_SIDEBAR` — toggle sidebar visibility (no payload)
- `SET_PITCHER_HITTER_SPLIT` — adjust pitcher/hitter split slider (number payload, 0-100)
