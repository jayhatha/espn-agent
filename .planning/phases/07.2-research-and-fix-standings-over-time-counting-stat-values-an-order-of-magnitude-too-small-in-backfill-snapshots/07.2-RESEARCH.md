# Phase 07.2: Research and fix standings over time - counting stat values an order of magnitude too small in backfill snapshots - Research

**Researched:** 2026-02-22
**Domain:** ESPN Fantasy Baseball API data structures, per-period stat accumulation, debugging data pipeline bugs
**Confidence:** HIGH

## Summary

This is a critical bug in the backfill code path added in Phase 07.1. Counting stats (HR, RBI, R, SB, K, W, SV) are appearing approximately 10x smaller than expected in backfilled snapshots (e.g., 2-3 HR when it should be 20-30). The bug is in `writeCurrentStandingsFromPlayerStats()` which accumulates per-period player stats from ESPN's `statSplitTypeId=5` data.

The root cause is likely one of these issues:

1. **Active roster filter too aggressive** - The code filters `entry.lineupSlotId <= 15` to exclude bench/IL/NA players, but this may be excluding valid starting lineup slots
2. **statSplitTypeId=5 returns per-game instead of per-week** - ESPN may use different split types (0=season, 1=last7, 2=last15, 3=last30, 5=per-scoring-period), and `statSplitTypeId=5` might return daily stats that need aggregation across the week's games
3. **Missing cumulative accumulation** - The code has logic for prior week accumulation (`previousSnapshotDate`), but if this isn't working correctly, each week resets instead of accumulating
4. **Roster slot filtering excludes active players** - ESPN's `lineupSlotId` mapping may differ from documentation, causing starters to be filtered out

**Primary recommendation:** Debug by logging the actual ESPN response structure for `statSplitTypeId=5` data, inspect how many players pass the active roster filter, and verify that week-over-week accumulation is working correctly.

## Common Pitfalls

### Pitfall 1: Assuming lineupSlotId Mapping is Correct

**What goes wrong:** Code filters `lineupSlotId <= 15` to get "active" players, but ESPN's slot IDs may not match documentation
**Why it happens:** ESPN API documentation is often incomplete or outdated
**How to avoid:** Log actual lineupSlotId values from real data and verify against ESPN_LINEUP_SLOT_MAP
**Warning signs:**
- Very few players pass the active roster filter
- Key players missing from week's stats
- Filter excludes slots that should be active (e.g., RP might be slot 15, DH might be slot 10)

**Verification:**
```typescript
// Check if critical slots are being excluded
const excludedSlots = rosterEntries
  .filter((e: any) => e.lineupSlotId > 15)
  .map((e: any) => e.lineupSlotId);
const uniqueExcluded = [...new Set(excludedSlots)];
// If you see 13, 14, 15 excluded, these are P/SP/RP - should be INCLUDED
```

### Pitfall 2: statSplitTypeId=5 Returns Unexpected Granularity

**What goes wrong:** Assuming `statSplitTypeId=5` returns week totals, but it might return per-game or daily stats
**Why it happens:** ESPN API uses undocumented stat split types
**How to avoid:** Inspect actual values for a known player/week and compare to expected totals
**Warning signs:**
- Stats are consistently small (2-3 HR instead of 20-30)
- Values look like single-game performance
- Ratio between expected and actual is consistent (suggests unit mismatch, not missing data)

**Verification:**
```typescript
// For a known star player, check their week stats
const ohtaniStats = periodStats.stats; // statSplitTypeId=5 for a specific week
const hrValue = ohtaniStats[5]; // ESPN stat ID 5 = HR
// If Ohtani hit 3 HR that week, should see 3
// If seeing 0.3 or 0.03, indicates wrong split type or unit
```

**Possible ESPN statSplitTypeId values:**
- `0` = Full season cumulative
- `1` = Last 7 days
- `2` = Last 15 days
- `3` = Last 30 days
- `5` = Unknown (assumed per-scoring-period, needs verification)

**Action if wrong:** May need different split type, or aggregate multiple split=1 (daily) entries across scoring period.

### Pitfall 3: Cumulative Accumulation Not Working

**What goes wrong:** Week-over-week accumulation broken, causing each week to start from zero
**Why it happens:** `previousSnapshotDate` logic doesn't load prior components correctly
**How to avoid:** Verify components_json in database shows increasing totals across weeks
**Warning signs:**
- Week 1 and Week 10 have similar small values
- No increasing pattern over season
- Prior components always empty/zero

**Verification:**
```typescript
// Query sequential weeks for same team
const weeks = await db
  .selectFrom("team_daily_category_totals")
  .select(["snapshot_date", "value", "components_json"])
  .where("league_id", "=", leagueId)
  .where("team_id", "=", teamId)
  .where("category_id", "=", "HR")
  .orderBy("snapshot_date", "asc")
  .execute();

// Should see increasing values: week1=5, week2=12, week3=18, etc.
// If seeing: week1=2, week2=3, week3=2 (small and flat), accumulation is broken
```

### Pitfall 4: Wrong scoringPeriodId to Date Mapping

**What goes wrong:** Fetching wrong week's data due to date math errors
**Why it happens:** Backfill computes `snapshotDate` from `scoringPeriodId` using heuristic (April 1 + 7*week offset)
**How to avoid:** Verify ESPN response actually contains the expected week's games
**Warning signs:**
- Stats present but wrong magnitude
- Inconsistent across teams (some correct, some not)
- Date-based bugs (off-by-one week)

**Verification:**
Check ESPN response's `scoringPeriodId` field matches what was requested.

## Likely Root Causes (Ranked by Probability)

### 1. Active Roster Filter Excluding Pitchers (HIGH probability)

**Evidence:** Code filters `lineupSlotId <= 15`, but ESPN lineup slots are:
- 13 = P (pitcher general)
- 14 = SP (starting pitcher)
- 15 = RP (relief pitcher)

If the filter is `<= 15` (which it is), pitchers SHOULD be included. But if there's an off-by-one error or misunderstanding of inclusive/exclusive bounds, pitchers could be excluded.

**Test:** Log how many players have `lineupSlotId` in range [13-15]. Should see 5-9 pitchers per team.

**Fix if confirmed:** Review filter logic, ensure `<=` is correct, check for edge cases.

### 2. statSplitTypeId=5 is Per-Game, Not Per-Week (MEDIUM-HIGH probability)

**Evidence:** Consistent 10x smaller values suggests unit mismatch. If a scoring period is ~7 days with ~6-7 games per team per week, per-game stats would be ~1/7th the week total, which is close to 10x smaller.

**Test:** For a player who hit 3 HR in a week, check if `statSplitTypeId=5` shows 3.0 or 0.43 (3/7).

**Fix if confirmed:** Either:
- Use different stat split type
- Aggregate all statSplitTypeId=5 entries for the scoring period's date range
- Multiply by games played (if ESPN provides game count)

### 3. Only One Day's Stats Being Captured (MEDIUM probability)

**Evidence:** If ESPN returns multiple `stats[]` entries per player (one per game), but code only processes first match, would capture 1/7th of week.

**Test:** Log `playerStats.length` and check if multiple entries have `statSplitTypeId=5` with same `scoringPeriodId`.

**Fix if confirmed:** Aggregate all matching stats entries, not just first.

### 4. Bench Players Actually Active (LOW probability)

**Evidence:** If most players are on bench (lineupSlotId=16) but should count, excluding them would drastically reduce totals.

**Test:** Check if bench players' stats should count in roto scoring. (They shouldn't in standard leagues, so this is unlikely.)

**Fix if confirmed:** Revise filter criteria based on league scoring rules.
